# Authentication and authorization tests

Generated by the plugin `scripts/design/generators/auth.ts`; identities resolved by `shared/fixtures/auth.ts`;
tokens obtained once by `shared/global-setup.ts`.

## Identities
| Identity | Source | Expected on protected endpoint |
|---|---|---|
| admin | `<API>_ADMIN_TOKEN`, `<API>_API_KEY`, or login with `<API>_USERNAME/_PASSWORD` | success |
| none | no header/cookie | `unauthenticatedStatus` (401) |
| invalid | random 40-char hex | 401 |
| expired | `<API>_EXPIRED_TOKEN`, else a synthetic JWT with `exp` in the past | 401 |
| malformed | bearer without prefix / cookie without value / broken Basic | 401 |
| wrongScheme | Basic instead of Bearer, or Bearer header instead of cookie/api key | 401 |

401 vs 403 follows the spec. If undocumented, 401 is expected (RFC 7235) and the case is marked as an
assumption; an API answering 403 is then a `Contract/Spec mismatch`, an API answering 2xx is a
`Real API defect` (security).

## Login endpoint
valid credentials -> token string at `login.tokenField`; wrong password, missing username, missing
password, empty body -> rejected (400/401/403/422) **and no token in the body**.

## Public endpoints
Must work with no token. For APIs without any auth scheme also check that an unexpected random bearer
token is ignored.

## One identity, no OAuth (user decision - do not reintroduce)
- Admin is the only credential identity. There are no normal-user (`user`, `user2`) or limited-scope
  identities, so no wrong-role (403) checks.
- OAuth2/OpenID flows are not run. Discovery records declared schemes (`auth.declaredSchemes`) but uses
  another scheme when one exists (PetStore: `api_key`); an OAuth2-only API becomes `bearer` with a ready
  access token in `<API>_ADMIN_TOKEN`. A login token is refreshed once on a 401/403.

## API keys and quotas
- For `apiKey` schemes the key (`<API>_API_KEY`) is sent on **every** request with the default identity,
  public endpoints included - keys identify the client and lift anonymous rate limits. Rejection checks
  (none/invalid/...) still send exactly what they test. A login session token is never put in the key header.
- On HTTP 429 with an exhausted quota (`x-ratelimit-remaining: 0`, `Retry-After`, or a rate-limit body) the
  test and every later test in that worker are **skipped** with the limit, reset time and how to raise it
  (`shared/helpers/quota.ts`) - never reported as failures.

## Credentials rule
- Values only from `.env` through `process.env`; never in specs, test data, reports or chat.
- Tests that need a credential call `requireCredentials('admin')` which **skips with a clear
  reason** when it is missing - never a silent pass. Rejection tests (none/invalid/expired/...) always run.
- The token lives in `process.env.__API_TOKEN_ADMIN` for the run only; reports redact `Authorization`/`Cookie`.

## Example
```ts
test('[TC_RESTFUL_BOOKER_BOOKING_ID_DELETE_012] DELETE /booking/{id} without a token is rejected with 401', async ({ api, data }) => {
  const input = data.entry('invalid', 'TC_RESTFUL_BOOKER_BOOKING_ID_DELETE_012');
  await api.withResource('booking', input.setupBody, async (id) => {
    const res = await api.send({ method: 'DELETE', path: '/booking/{id}', identity: 'none', ...fromData(input, { id }) });
    expectNoServerError(res);
    expectStatus(res, [401]);
    expectErrorBody(res, 'safe');
    expectResponseTime(res, limits.responseTimeMs);
  });
});
```
